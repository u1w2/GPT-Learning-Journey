# Stage 02｜System Design

> 当前阶段。正在训练：API Design。
>
> Cursor 不得在学习者独立作答前给出 API Question 1 的标准答案。

## 1. 能力定位

把“能把功能做出来”升级为“能在约束下设计系统边界、接口、数据和演进策略”。

当前只训练 API Design，不提前展开缓存、消息队列、服务拆分。

## 2. 为什么需要

第一阶段为了快速验证，Web、小程序、后台管理端都要调同一套 API。如果第一阶段只图快、不处理契约边界，后面每增加一个客户端都会变成兼容和重构。

## 3. 前置能力

- 能识别业务对象和访问关系
- 能区分当前约束和未来想象
- 能接受“没有证据就不能引入复杂度”

## 4. 核心知识

本阶段先围绕 API 契约，而不是组件清单：

- 资源与操作如何表达
- 客户端演进如何影响兼容
- 哪些决策现在必须冻结
- 哪些决策现在冻结会过度设计

后续知识点必须等当前问题暴露后再打开。

## 5. 必须形成的能力

- 独立回答：第一阶段 API 必须确定什么
- 区分“现在必须定”和“刻意延后”
- 能解释为什么，而不是列出名词
- 能接受 Review 和追问

## 6. 项目任务

当前项目任务尚未开始。API Question 1 通过后，再决定是否进入可运行 API 项目。

不要为了“看起来完整”先搭微服务。

## 7. Test Lab / 实验

当前还没有实现，因此还没有压测。Question 1 的验收是架构判断，不是 QPS 数字。

进入实现后，实验必须主动制造兼容问题，而不是只测 happy path。

## 8. 常见短板

- 只设计当前三个客户端，不考虑第 N 个客户端
- 反过来为了“未来所有可能”把版本、网关、BFF、GraphQL 一次做完
- 把内部表结构直接暴露成 API
- 只谈 URL，不谈错误、鉴权、幂等、分页、兼容策略

## 9. 验收标准

Question 1 通过，不要求答案“完整得像清单”，而要求：

1. 学习者独立作答
2. 能说明为什么这些必须第一阶段确定
3. 能说明什么现在不要定
4. 能解释不做这些以后会如何重构
5. 经 Review 后能补上被指出的遗漏，而不是改口背答案

## 10. 面试迁移

后续应能不看文档回答：

> 多个客户端共用 API 时，你第一阶段会冻结哪些契约？为什么？

## 11. 下一阶段关联

System Design 站稳后，才进入 Software Architecture。没有 API 边界，谈分层、模块和演进没有锚点。
